## 一、严重级（崩溃 / 回归 / 数据销毁）

### 1. 查询"未持仓标的"时直接崩溃
- **位置**：`backend/app/market/digital_human_tools.py:702`
- **影响**：调用 `get_position_decision_context(symbol, account_id=5)`，但账户 5 里没有这只股票的持仓时，代码会去取空列表的第一个元素，抛 IndexError 崩溃。而"查询某账户里还没建的仓"是合法且常见的操作（比如研究要不要建仓），一崩 agent 这一轮的决策上下文就断了。
- **修复收益**：未持仓时正常返回 `position=None` 并继续给出研究/决策上下文，工具不再中断 agent 流程。

### 2. 一个退市代码导致全部持仓价格都不更新（回归）
- **位置**：`backend/app/scheduler/rhythm_scheduler.py:516`
- **影响**：持仓价格同步从"逐个标的取价"改成了"一次性批量取全部标的"。只要持仓里有一个退市/无效代码，整批行情接口返回 error，代码 `raise RuntimeError`，于是**全部 50 个持仓**（含 49 个正常的）价格都不更新，每分钟重复一次，直到删掉那个坏代码。旧代码是逐个取、坏的那个跳过、其余照常。
- **修复收益**：恢复"坏标的跳过、其余正常同步"的韧性，单个异常代码不再拖垮全局价格刷新，所有正常持仓的价格保持新鲜。

### 3. 清空数量框 → 以 0 股覆盖真实持仓（数据销毁）
- **位置**：`frontend/src/components/PositionsWorkbench.vue:637`
- **影响**：OCR 识别出某行持仓数量 1000，用户不小心清空了数量输入框，`v-model.number` 得到空字符串 `''`，而 `Number('')===0` 能通过"非负/有限"校验，确认入库时以 `action:'replace'` 发送数量 0，后端把 1000 股的真实持仓覆盖成 0 股——静默数据销毁，无任何提示。
- **修复收益**：清空/非法数值时拦住确认并提示用户，真实持仓不会被一次误操作清零。

## 二、高级（功能性错误 / 资源 / 一致性）

### 4. 重启就恢复用户禁用的内置任务
- **位置**：`backend/app/scheduler/rhythm_scheduler.py:1008`
- **影响**：`ensure_default_jobs` 在每次启动时无条件重置内置任务（含 `enabled=True`、间隔、窗口），尽管注释写的是"版本升级时迁移"。用户通过管理接口禁用了价格同步任务以省 TuShare 调用，一重启又被改回启用，每分钟又开始刷，偏好被静默覆盖。
- **修复收益**：用户的禁用/排期定制在重启后保留，内置任务的"启用/禁用"状态真正可控。

### 5. 图片读取失败 → 拿旧截图当新截图 OCR
- **位置**：`frontend/src/App.vue:473`
- **影响**：拖入新截图 B，若文件读取失败（网络/锁定/已移动），文件名已先设成 B，但 base64 仍是上一张 A 的数据，且没有 try/catch 兜底。下一次发送时把 A 的图片当 B 发出去，agent 对着错的截图做 OCR，用户毫不知情。
- **修复收益**：读取失败时清状态并提示重选，杜绝"文件名是新的、内容是旧的"错位。

### 6. 涨跌停时间线分类完全失效（字段名对不上）
- **位置**：`backend/app/market/company_research.py:70`
- **影响**：`_market_timeline` 读 `limit`/`status`/`up_stat`/`first_time`/`last_time`，但 `get_limit_list` 实际返回的字段是 `limit_status`/`first_break_time`/`last_break_time`。全部对不上，导致状态恒空、时间恒空、所有记录都被打成笼统的"涨跌停记录"，分不出涨停/炸板。原始数据还在，但给 agent 看的时间线是坏的。
- **修复收益**：正确识别涨跌停类型和封板时间，公司研究的时间线证据真实可用。

### 7. 平盘股（涨跌幅 0.0）被错报成前日涨幅
- **位置**：`backend/app/market/company_research.py:332`
- **影响**：`pct_chg = latest.get('pct_chg') or latest_bar.get('pct_chg')`，Python 里 `0.0` 是假值，所以今天平盘（0.0）会被 `or` 替换成前一天的涨跌幅。研究包把昨天的涨幅当成今天的报给 agent。
- **修复收益**：平盘就是平盘，涨跌幅数据准确，不误导后续估值/技术分析判断。

### 8. 重复提交 → 持仓快照表堆积重复行
- **位置**：`backend/app/main.py:632`
- **影响**：OCR 确认接口对 `image_sha256` 没有幂等处理，模型表也没有唯一约束。用户双击确认、或网络重试，同一张截图会生成多份导入批次和重复快照。读取取最新快照所以展示是对的，但表会持续膨胀。
- **修复收益**：同一截图只入库一次，批次/快照表不再因重试而堆积冗余行。

### 9. per-row account_id 能覆盖服务端校验过的账户
- **位置**：`backend/app/main.py:647`（合并发生在 `position_agent.py:987`）
- **影响**：确认接口校验了顶层 `payload.account_id` 属于该用户，但构造 rows 时没剔除客户端塞进单行的 `account_id`，而 `merged={**default_account,**row}` 让单行值覆盖了校验值。恶意/有 bug 的客户端能把某行写到自己的另一个账户（跨用户被 `_owns` 挡住，但账户间错位能发生）。
- **修复收益**：以服务端校验过的账户为准，单行无法篡改写入账户，消除账户错位风险。

## 三、中级（UX / 显示 / 类型）

### 10. 清空成本价 → 发空字符串而非数字
- **位置**：`frontend/src/components/PositionsWorkbench.vue:647`
- **影响**：清空成本价/最新价输入框，`v-model.number` 得到 `''`，确认时只对数量做了 `Number()` 转换，成本价原样发出 `""` 字符串，违反类型契约（应为 number|null）。后端按字符串处理，存成错误成本或逐行报错，提示信息误导。与第 3 条同根因。
- **修复收益**：成本价字段统一成数字或 null，入库语义一致，不再出现空字符串造成的怪异报错。

### 11. 每次开抽屉都重置用户手选的模型
- **位置**：`frontend/src/App.vue:417`
- **影响**：`loadPositionModels` 每次开持仓 agent 抽屉都把选中模型重置成"按硬编码名字 qwen3.7-plus/k3 优先"的那个，用户上次手选的模型 B 被静默换掉，下一次 OCR 跑在另一个模型上，无人察觉。硬编码模型名本身也脆弱。
- **修复收益**：用户手选的模型在抽屉关闭/重开后保留，OCR 始终用用户指定的模型，偏好不被覆盖。

### 12. 达到最大迭代上限的错误信息被覆盖（可能）
- **位置**：`backend/app/agent_runtime/agentscope_engine.py:1352`
- **影响**：`ExceedMaxItersEvent` 分支设了"已达 N 次最大推理迭代上限"的有用错误，但没 `break`（另两个失败分支都 break 了）。如果之后还来一个 `ReplyEndEvent`（finished_reason 非 completed/interrupted），会把这条有用信息覆盖成笼统的"AgentScope ended: xxx"。触发取决于 AgentScope 是否在超限后还发 ReplyEnd 事件，故标"可能"。
- **修复收益**：超限错误信息保留，用户/排查时能看到"是迭代超限、需拆分任务"这个可操作的提示，而非一句无意义的状态码。

### 13. 用方案B/方案C 的报告被误判"缺方案"（可能）
- **位置**：`backend/app/agent_runtime/evidence_service.py:671`
- **影响**：审计逻辑只认"方案A/情景A"才算有方案，且只数方案A/B。一份用"方案B+方案C"两条有效方案、但不带 A 的报告，会被判成"缺少方案"标为 incomplete。生产路径在本提交是否真正走到尚未完全确认，故标"可能"。
- **修复收益**：只要满足两种条件化方案即判通过，不因命名不含 A 而误杀合格报告。

### 14. 校验进行中点确认 → 被误拒
- **位置**：`frontend/src/components/PositionsWorkbench.vue:588`
- **影响**：编辑完股票代码失焦触发校验（进行中），用户立刻点"确认入库"，该行因 `row.validating` 立刻返回 false，界面提示"仍有股票代码未通过校验"，但校验其实马上就通过了。用户得再点一次。无数据损失，但体验差。
- **修复收益**：校验进行中时确认能正确等待结果，不再出现"明明通过了却被拒"的假阴性。

### 15. 非整数数量被显示成 `1,`（OCR 误读时）
- **位置**：`backend/app/agent_runtime/agentscope_engine.py:649`（调用在 686）
- **影响**：数量字段用 `digits=0` 格式化后做 `.rstrip('0').rstrip('.')`。若 OCR 把数量误读成非整数（如 1000.5），会格式化成 `1,000` 再被 rstrip 成 `1,`，用户在确认前看到的草稿表里数量成了 `1,`。整数数量走另一分支不受影响。
- **修复收益**：草稿表数量展示正确，用户基于准确数值决定是否入库。
