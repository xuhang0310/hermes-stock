# 数字人能力升级方案

> 日期：2026-11-03
> 进度：第 8 节全部按默认值确认（2026-11-04）。阶段 0 已实现，待部署后在飞书上验收（见 1.7）；阶段 1–4 未开始。
> 依据：生产库近 30 天运行记录（只读统计）与当前代码。
> 一句话：数据工具已经够用，接下来要让数字人**看得懂自己的计划、到价马上提醒、知道自己判断准不准、消息来了主动处理**；客户在飞书上除了文字，还能点开一个适配手机的完整网页。

## 0. 现状

| 方面 | 现状 | 问题 |
|---|---|---|
| 数据工具 | 59 个工具 + TuShare 179 个接口 + 联网搜索 + 知识库 | 够用，不是瓶颈 |
| 盘中提醒 | 盘中哨兵每 30 分钟一条；持仓价格每分钟刷新 | 没有“到价提醒”，碰到计划价最慢要等半小时才知道 |
| 挂单清单 | 早盘、午盘清单只有文字（`notes/reviews/{date}/premarket.md`） | 系统读不懂计划，没法自动盯价，也没法和实际成交对账 |
| 自我复盘 | 经验库 `experience_entries` 0 行；预测台账只写在 JSONL 文件 | 数字人不知道自己过去的判断准不准 |
| 消息 | 新闻每 15 分钟入库一次 | 入库时不标股票，也不触发分析；公告没有入库 |
| 专家分工 | 8 个启用的定时任务里，6 个由总调度跑，2 个由盘中哨兵跑 | 风控官、情报官基本没参与日常流程 |
| 飞书推送 | 卡片里放全文，长报告自动拆成多张卡片 | 手机上表格被拆成一行行文字（`_linearize_markdown_tables`），长文要翻好几张卡片 |

**地基是“计划结构化”**：触价提醒、成交对账、战绩回看、风控复核、手机页面上的实时状态，都建立在“系统读得懂计划”这件事上。

## 1. 改进一：飞书推送附带手机版网页链接

### 1.1 客户看到什么

飞书卡片保持现在的全文不变，在第一张卡片的元信息下面、最后一张卡片的页脚上面各加一个按钮：

```

│ 早盘挂单清单 | 2026-11-04            │  ← 卡片标题（不变）
├────────────────────────────────────┤
│ 任务：早盘挂单清单  数字人：A股研究总调度  │
│ 生成时间：2026-11-04 08:52:10        │
│ ┌────────────────────────────────┐ │
│ │      📱 手机查看完整版            │ │  ← 新增按钮
│ └────────────────────────────────┘ │
├────────────────────────────────────┤
│ 正文（不变）……                       │
└────────────────────────────────────┘
```

```

├──────────────────────────┤

│ │ 状态：待触发 · 现价 22.35│ │  ← 计划页显示实时状态（见 2.6）
│ └──────────────────────┘ │
```

### 1.2 链接怎么生成

新表 `report_shares`：

| 字段 | 说明 |
|---|---|
| `share_id` | 主键，`secrets.token_urlsafe(16)`（128 位随机，不可猜） |
| `owner_user_id` | 归属用户 |
| `source_type` | `agent_report` / `trade_plan` / `price_alert` / `event_brief` / `chat_reply` |
| `source_ref` | 对应的 `report_id`、计划 ID 等 |
| `title`、`meta_json` | 标题，以及任务名、数字人、生成时间、数据日期 |
| `content_md` | 推送时的正文快照（和飞书卡片同一份，经过白话改写之后的版本） |
| `created_at`、`expires_at`、`revoked_at` | 默认 30 天有效，可以手动作废 |
| `view_count`、`last_viewed_at` | 打开次数，便于知道客户看没看 |

- 入口：`send_feishu()` 加一个可选参数 `share`。传了就先建分享记录、拼出链接，再生成卡片。
- `_run_agent_report`（定时报告）、选股推送、早盘舆情简报、触价提醒、消息解读都走这个入口。
- 新配置：
  - `STOCK_PUBLIC_BASE_URL`，例如 `https://shijingxuan.com`。没配就不加链接，推送照旧。
  - `STOCK_SHARE_TTL_DAYS`，默认 30。
- 链接形式：`https://shijingxuan.com/api/share/{share_id}`。走现有 nginx 的 `/api/` 转发，不用改 nginx。
  - 想要更短的 `/s/{share_id}`，在 `deploy/nginx/hermes-stock.conf` 里加一条 `location /s/` 转发到后端即可。

### 1.3 页面怎么渲染

- **服务端直接出 HTML**：`GET /api/share/{share_id}` 返回一个自包含页面，CSS 内联，不依赖前端打包、不加载任何外部资源。
  - 飞书内置浏览器打开快。
  - 前端改版也不会影响这个页面。
- **渲染库**：后端新增 `markdown-it-py`（解析）和 `nh3`（白名单清洗，防 XSS）两个依赖。
  - 前端 `utils/markdown.ts` 对中文旁 `**粗体**` 的放宽规则要移植过来，否则 `**结论：**后文` 在网页上不会变粗。
- **手机适配**：
  - `viewport` 设为设备宽度，正文 16px、行高 1.7、左右留 16px，内容最宽 720px 居中，不会出现横向滚动。
  - 普通表格放进可横向滑动的容器，第一列固定。
  - 计划表（账户 / 股票 / 怎么做 / 价格 / 股数）在窄屏上改成一行一张卡片，价格和股数加粗，用等宽数字。
  - A 股配色：红涨绿跌，买入红、卖出绿；止损类单独用醒目底色。
  - 跟随系统深色模式（飞书的深色模式会传到内置浏览器）。
  - 长文（超过 3 个二级标题）顶部给可折叠的目录，标题带锚点。
  - 第一段结论加底色高亮。
  - 页脚只写生成时间和链接有效期，不加免责套话（卡片页脚已有）。
- 页面大小目标 50KB 以内，没有任何脚本。

### 1.4 安全与隐私

页面里有客户的持仓、股数和金额，所以：

- 链接本身就是凭证：128 位随机 ID，有有效期，可作废。打开时检查是否过期或作废，失效时给一个友好提示页。
- 响应头：
  - `X-Robots-Tag: noindex`
  - `Referrer-Policy: no-referrer`
  - `Cache-Control: private, no-store`
  - CSP 设为 `default-src 'none'; style-src 'unsafe-inline'; img-src data:`
- 不放 Open Graph 摘要：飞书解析链接预览时，抓不到正文内容。
- `report_shares` 不登记进 `sql_sandbox`，数字人查不到分享 ID。
- 注意：飞书卡片现在允许转发（`enable_forward: True`），客户把卡片转出去，链接也会跟着出去。是否收紧，见第 8 节。

### 1.7 实现记录（2026-11-04）

和上面设计不同或多做的地方：

- **按钮**：消息只有一张卡片时只放顶部一个，多张时第一张和最后一张各一个。
- **分享 ID**：用 `secrets.token_hex(16)`（同样 128 位）。MySQL 默认排序规则不分大小写，全小写才能保证一个 ID 只对上一行。
- **`source_type`**：目前有 `agent_report`、`selection_digest`、`topnews_brief`、`channel_test`；`trade_plan` 等随后面阶段增加。同一 `source_ref` 重发时复用同一条链接；舆情简报没有稳定的来源 ID，每次是新链接。
- **页面没有“数据截至”一行**：系统现在拿不到结构化的数据日期，不编造；正文开头一般已写明。等阶段 1 有结构化计划再加。
- **长文字表也用卡片**：三列以上、有单元格超过 24 字的表，窄屏下同样一行一张卡片（不上操作色）。真实报告里这类表横向滑动很难读。
- **操作列上色只看第一小句**：“拿着，跌破 12 止损”“不参与：不再买”不上色。
- **飞书拒收的兜底**（方案没写）：飞书对带按钮的卡片返回业务错误时，去掉按钮整条重发并写告警，报告不会因为按钮送不到。
- **验收入口**（方案没写）：配置页“测试”按钮发的卡片带按钮，点开是 1 天有效的虚构示例页。
- **部署**：`scripts/deploy.py` 在 `.env` 没有 `STOCK_PUBLIC_BASE_URL` 时写入 `https://shijingxuan.com`，下次部署后功能即开启。
- **管理接口没有前端页面**：`GET /api/shares`、`POST /api/shares/{id}/revoke` 目前只能调接口用。

已验证：单元测试（XSS 清洗、过期和作废、权限、卡片结构、拒收兜底）；真实报告在 Chrome 中按 320/390/700px 渲染，没有整页横向滚动；真实响应头下样式正常；深色模式正常。

未验证（需要部署后在飞书上看）：飞书真实接受这个按钮结构；iOS、Android 飞书内置浏览器的显示和深色模式。

## 2. 改进二：挂单清单结构化 + 到价即时提醒

### 2.1 结构化计划

两张新表，都登记为 `sql_sandbox` 的个人表（数字人只能查到自己用户的计划）：

**`trade_plans`**（一份计划）

| 字段 | 说明 |
|---|---|
| `plan_id`、`owner_user_id`、`plan_date` | |
| `source` | `premarket` / `midday` / `evening` / `weekly` / `monthly` / `selection` |
| `report_id`、`run_id`、`digital_human_code` | 关联到哪份报告、哪次运行 |
| `status` | `active` / `superseded`（被午盘调整替代）/ `expired` |

**`trade_plan_items`**（一条操作）

| 字段 | 说明 |
|---|---|
| `account_id`、`symbol`、`name` | 哪个账户、哪只股票 |
| `action` | `buy` / `sell` / `add` / `reduce` / `hold` / `stop_loss` / `cancel` |
| `trigger_type`、`trigger_price` | `limit`（挂单价）/ `rise_to`（涨到）/ `fall_to`（跌破）/ `none`（拿着不动） |
| `quantity` | 股数 |
| `funding_note` | 钱从哪来，例如“用卖同力天启的钱” |
| `valid_until` | 默认当天收盘 |
| `status` | `pending` / `triggered` / `executed` / `partially_executed` / `expired` / `superseded` |
| `triggered_at`、`triggered_price`、`notified_at` | 触价记录 |
| `executed_qty`、`trade_ids` | 和实际成交对账的结果 |

### 2.2 数字人怎么交出结构化计划

- 新工具 `save_trade_plan`，只给早盘、午盘、晚间、周、月计划这几类定时任务用。数字人写完文字清单后，调用一次，把同样的内容按字段交上来。
- 工具当场校验，不合格就把原因返回给数字人，让它改：
  - 股票必须在持仓、自选或当天选股名单里。
  - 卖出股数不能超过可卖数量。
  - 股数按交易规则取整：一般 100 股，科创板至少 200 股。
  - 价格在当日涨跌停范围内（`get_stk_limit`）。
  - 同一账户的买入金额不能超过现金加上写明来源的当天卖出款，同一笔钱不能算两次。
- 文字和结构化计划要一致：保存后检查每条“股票 + 价格 + 股数”都能在文字里找到，思路和白话改写的 `check_facts_kept` 一样。对不上就让数字人改一次，还对不上就在报告末尾注明。
- 午盘调整保存后，早盘计划自动标为 `superseded`，避免同一只股票重复提醒。
- 提示词只需要加一句“写完清单后用工具把计划存下来”，不写工具名以外的规则（规则都在工具校验里）。

### 2.3 盯价

- 挂在现有的每分钟持仓价格同步上（`sync_position_prices`）。刷新完价格后，顺带检查当天所有 `pending` 的计划条目，不调用模型，没有额外成本。
- 计划里买入的自选股不在持仓里，要把这些代码加进每分钟刷新的列表。
- 判断规则：
  - 涨到、挂单卖：价格 ≥ 计划价。
  - 跌破、止损、挂单买：价格 ≤ 计划价。
  - 两次刷新之间的尖峰用当日最高价、最低价补上。基准取计划生成那一刻的最高价、最低价，避免午盘计划被上午的高点误触发。
- 去重：每条只提醒一次。同一分钟触发的多条合成一张卡片。

### 2.4 提醒长什么样

```
⚡ 触价提醒 · 09:47
方正账户｜同力天启 现价 24.15
碰到早盘计划：涨到 24.13 卖 500 股
价格碰到不等于成交，以券商为准。
成交后在飞书回一句“方正卖了同力天启 500 股 24.15”，系统会记账。
[📱 打开今天的计划]
```

- 止损类用红色卡片，普通到价用橙色。
- 链接打开的是计划页（见 2.6），能看到当天所有条目的实时状态。

### 2.5 成交对账

- 客户在飞书或网页上记的成交（`position_trades`），按“账户 + 股票 + 方向 + 计划生成之后”匹配到计划条目，更新为 `executed` 或 `partially_executed`。
- 晚间日报里“计划和实际对照”那一段，改为直接读对账结果，不用再让数字人自己去翻文件比对。数字最准，也更省时间。

### 2.6 计划页

`source_type = trade_plan` 的分享页每次打开时都实时渲染：按账户分组，列出每条计划的状态（待触发 / 已触发 9:47 @24.15 / 已成交 500 股 / 已过期）和最新价。客户在手机上一页就能看清今天进行到哪一步。

### 2.7 验收

- 早盘清单跑完，库里有结构化计划，条数、价格、股数和文字一致。
- 测试环境模拟价格穿过计划价，1 分钟内推出提醒，同一条不会重复提醒。
- 午盘计划生效后，早盘条目不再触发。
- 录入一笔成交后，对应条目变为已成交，晚间日报的对照段落数字正确。

## 3. 改进三：战绩回看与自我校准

> 和《自我进化实施方案》第 4.2 节“经验库进化”、第 4.5 节“论点存活监测”衔接，是它们的第一块落地。

### 3.1 怎么算对错

每条计划条目在 T+1、T+5、T+20 收盘后自动回看。跨交易日比价一律乘以 `stock_adj_factors` 复权因子，缺因子就记为缺失，不拿原始价凑数。

| 操作 | 算“对”的口径 |
|---|---|
| 卖出 / 减仓 | 触发后 N 日收盘价低于触发价（卖对了，避开了下跌） |
| 止损 | 触发后 N 日没有收回止损价以上 |
| 买入 / 加仓 | 触发后 N 日收益跑赢同期沪深 300 |
| 拿着不动 | N 日内最大回撤没超过计划里写的止损幅度 |
| 没触发 | 单独统计“价格定得太远”的比例 |

结果存进 `trade_plan_item_outcomes`：条目、N、收益、基准收益、是否算对、是否实际执行。

### 3.2 怎么用起来

- **数字人战绩页**：放在数字人中心，按数字人、操作类型列出次数、准确率、平均收益。样本少于 20 条的标“样本不足”。
- **校准提示**：早盘、午盘等出计划的任务，开头自动注入一段 200 字以内的近期战绩，例如“近 60 个交易日：止损建议 18 次，5 日后看对了 13 次；追高买入 9 次，对了 3 次”。数字人自己决定怎么调整，系统不替它改规则。
- **进入经验库**：样本够、统计上站得住的结论写进经验库 `experience_entries`，走现有的经验注入通道。
- **防自欺**：只提供信息，不自动改提示词或策略。口径固定写在代码里，不让数字人自己挑对自己有利的算法。

### 3.3 验收

- 历史计划能回填战绩。用 11 月以来的计划回算，数字和人工抽查一致。
- 出计划的任务提示词里能看到战绩段落，长度不超过 200 字。

## 4. 改进四：消息驱动

### 4.1 消息来源

- **公告**：交易时段和盘前每 15 分钟，晚上 19:00–22:00 每 30 分钟，用 TuShare `anns_d` 拉持仓和自选股的新公告（工具 `get_anns` 已有，只缺定时入库）。
- **新闻**：现有快讯和要闻入库时，按股票名称和代码匹配持仓、自选，写入 `document_symbols`（现在入库时不标股票）。

### 4.2 过滤

- 先用规则筛，不调用模型：业绩预告或快报、增减持、回购、重大合同或中标、问询函或监管函、立案、诉讼、质押或冻结、停复牌、重组、退市风险、分红送转。
- 按内容哈希去重；同一只股票 1 小时内只处理一次；每天最多解读 10 条，控制成本。
- 次要消息不单独推送，并进下一条盘中提醒。

### 4.3 处理

- 重要消息交给情报官跑一个短任务：
  - 这条消息说了什么，靠不靠谱。
  - 影响有多大，会不会改变今天的计划。
  - 如果要改，怎么改（价格和股数）。
- 推送一张卡片并附网页链接；计划页上受影响的条目标注“消息待复核”。
- 推送时间：07:30–22:30 即时推。夜里的消息并入第二天早盘清单。停牌、立案这类重大利空例外，随时推（可配置）。

### 4.4 验收

- 回放一条历史公告，能识别出对应股票，规则判为重要，推出解读，同一条不重复。
- 一天的模型调用次数在上限以内。

## 5. 改进五：大动作先过风控复核

### 5.1 范围

只用在晚间日报、周计划、月计划（时间不敏感）。早盘、午盘不加，避免拖慢。

### 5.2 怎么判断“大动作”

由结构化计划自动判断：
- 单只卖出超过持仓的四分之一，或清仓。
- 新买单只超过账户总资产 5%。
- 给浮亏股加仓。

### 5.3 流程

1. 总调度出草稿，并保存结构化计划。
2. 有大动作时，调度器接着跑一个风控官任务：输入草稿和这些条目，逐条给出“同意 / 有保留 / 反对”，附一句理由和成立条件。
3. 最终推送的是草稿加上“风控意见”一段。计划条目上记 `risk_review`，网页上显示徽标。
4. 风控任务失败或超时（上限 10 分钟），照常推送草稿，末尾注明“风控复核未完成”。

这条流程以调度器后处理的方式实现，比套“投资决策委员会”工作流简单可控。工作流仍保留给手动深度复核用。

### 5.4 验收

- 有大动作的日报多出风控意见段落，网页上有徽标。
- 没有大动作时，流程和现在一样。
- 风控失败不影响日报送达。

## 7. 不变的边界

- 只研究和提醒，**不下单、不连券商**。所有提醒都写明“价格碰到不等于成交”。
- 计划和成交只记在系统里，持仓以客户登记为准。
- 新表登记进 `sql_sandbox`：计划类登记为个人表，按用户隔离；`report_shares` 不对数字人开放。
- 每个阶段都有单元测试（触价判断、股数校验、HTML 清洗、链接过期），不跑会写生产库的全量测试。
