# 行业分析整合方案

日期：2026-09-19。状态：首版已实现并通过本地验收，尚未部署到正式服务器。后续阶段仍为规划。

## 本次实现与验收

- 入口：量化参数 → 行业分析，支持直接访问 `/industries`。
- 已实现：行业热力图、强弱榜、搜索、按涨幅/成交额/上涨占比排序、行业广度、成分股分页和排序、携带行业条件进入选股、携带日期进入问股、加入当前用户自选。
- 接口：`GET /api/industries/overview`、`GET /api/industries/members`；后者必须带前者的 `snapshot_id`。行情变化时返回 409，前端引导刷新，防止概览与成员混用。
- 使用现有表，无数据库迁移。仅查询本地行情，不自动调用外部行情接口或模型；写自选复用现有用户隔离接口。
- 分类为当前 TuShare stock_basic 单层行业，仅计入沪深北 A 股，排除基金、B 股、已退市及尚未上市标的。缺失、零成交量及不完整日线不计作平盘。
- 选取近 120 天内日线覆盖达到 90% 的最新已收盘日期；若没有达到门槛，则展示最新可用日期并标明覆盖不足。90% 是覆盖门槛，不是完整性承诺。没有可靠本地交易日历时提示无法确认新鲜度。
- 成交额严格使用 TuShare daily 的千元口径换算为亿元；每日指标只连接同日记录，缺失显示为 `—`。行业等权涨幅不等于官方指数。
- 继续选股只传递行业条件，沿用选股器现有最新缓存口径，不声称复现行业页的历史截面。
- 只读实库核验：选取 2026-09-17，110 个行业，5,567 只 A 股目录中 5,554 只有当日日线；2 只缺行业。同日每日指标覆盖为 0，页面如实提示。2026-09-18 仅部分日线可用，系统回退并提示同步。
- 验证：后端行业及选股回归 29 项、前端 83 项通过，`npm run build` 通过；浏览器验证桌面/窄屏布局、热力图联动、分页、排序、行业条件传递，自选回显在本地模拟接口验证。

测试命令：

```text
python -m pytest tests/test_industry_analysis.py tests/test_screener_factors.py tests/test_screener_recommendations.py -q
cd frontend
npm test
npm run build
```

本轮未实现历史轮动、RPS、申万分级、行业资金流和自动选股行业强度因子。这些属于下面的后续阶段。

本方案基于当前 SixRabbits Stock 和已部署 TSP 的源码核查。没有把数据库字段存在当成生产数据已齐备，也没有实测 TuShare 行业接口的当前账户权限。

## 1. 产品目标

在现有系统新增「行业分析」，形成一条连续的研究路径：

行业强弱 → 行业内个股排名 → 个股问股 → 自选与条件选股 → 后续跟踪。

首版采用现有 TuShare 股票基础行业分类和最近完整交易日的日线口径。行业强弱由确定性计算产生，AI 负责按需解释和核实原因。

| 行业字段同步 | `backend/app/market/market_sync.py` 的 `_stock_catalog_rows`、`_upsert_instruments` | 复用现有目录同步，核查实际覆盖率 |

| 条件选股 | `quant/screener_api.py`、`quant/screener_service.py` | 增加行业条件，复用现有筛选与结果流程 |
| 个股问股入口 | `frontend/src/App.vue` 的 `openScreenerStockAnalysis` | 提取可复用入口，带上行业、统计日期和个股事实快照 |
| 自动选股行业约束 | `quant/automatic_selection_scoring.py` | 已有行业覆盖门槛及行业集中度约束；行业强度评分仍需新增 |
| 行业扩展接口 | `market/tushare_catalog.py`、`market/stock_tools.py` | 已登记申万分类、成分、日线和行业资金流接口；权限、数据完整性及持久化需要验证 |

方案制定时没有独立的行业分析页面，本次已补充。TuShare 接口目录存在，不等于行业历史数据和分级成分关系已经落库。

## 3. 首版页面

入口放在现有「量化参数」菜单，与 AI 选股、自动选股相邻。使用现有 Vue 3、FastAPI、MySQL 和登录权限体系。

| 区域 | 展示内容 | 交互 |
| --- | --- | --- |
| 市场概览 | 行业数量、上涨/下跌行业数、领涨行业、成交最活跃行业 | 显示统计日期、分类来源和有效样本覆盖 |
| 行业强弱榜 | 等权平均涨跌幅、中位数、上涨家数占比、成交额、活跃度 | 按涨幅、成交额、上涨占比排序；搜索行业 |
| 行业热力图 | 红涨绿跌，方块大小按有效成交额或成分股数 | 点击与右侧行业详情联动；无数据单独显示 |
| 行业详情 | 成分股清单、涨跌幅、成交额、换手率、量比、市值 | 排序、查看个股、加入自己的自选池、进入问股 |
| 个股排名 | 行业内涨幅榜和成交额榜；可选透明的综合活跃度分 | 展示分项与数据完整性，不把活跃度称为买入信号 |
| 研究联动 | 当前行业进入 AI 选股；个股携带上下文进入问股 | 用户点击后才提交研究问题，不在打开页面时调用模型 |

行业平均涨跌幅应命名为「成分股等权涨跌幅」，与官方行业指数的涨跌幅区分。成交额不能显示成「主力净流入」。

## 4. 数据和评分口径

1. **统一日期**：优先使用最近完整同步的交易日。日线、每日指标和统计日期对齐；不能混合不同日期的每股最新价后标成当天全市场。
2. **覆盖可见**：返回应覆盖、有效覆盖、缺行业、缺行情、停牌或过期数据数量。缺失涨幅不计入平盘，停牌不自动计入当天可交易样本。
3. **来源与单位**：现有行情表可能包含不同来源，需按来源确定成交额单位及去重优先级；不能直接对所有记录求和。涨跌幅百分数与小数也统一后再计算。
4. **行业分类**：首版使用单层 stock_basic 行业。申万、同花顺、中信分类将来分别存储，不能仅凭名称或字符串拆分推断层级。
5. **透明评分**：首版先提供客观分项榜。若增加行业热度/个股综合活跃度，使用公开的分项与权重，记录版本和可用字段；数据不足时不给完整评分。权重是产品规则，不代表已验证的超额收益能力。
6. **历史口径**：历史轮动需明确当时的行业成分；当前成分回溯只能作为带说明的研究视图。多日涨幅先验证复权和除权处理，不能直接把未复权价格跳变当成行业轮动。

首版页面只读本地共享行情。同步操作复用既有机制，不在每次刷新页面时逐行业或逐股票调用外部接口。

拟提供 `GET /api/industries/overview` 和 `GET /api/industries/members?industry=...`。接口名称为提案，当前尚不存在。

首版不必新建完整的行业数据库体系，可先基于现有表完成聚合。性能验证后按「交易日 + 行业分类 + 数据版本」缓存；数据刷新时统一失效，不能长期依赖进程内过期缓存。

行业市场统计是共享数据；加入自选、持仓标记及研究记录沿用当前用户作用域，不把个人持仓或自选混入共享聚合缓存。

## 6. 分阶段交付

**阶段一：可用的日线行业工作台。** 完成数据覆盖核查、统一聚合、强弱榜、热力图、成分股榜、问股、自选与行业条件选股。保留清晰的空数据、过期和部分覆盖状态。

**阶段二：行业分级和历史轮动。** 验证申万等数据权限，增加行业分类及带生效日期的成员关系，补齐行业指数历史；提供 5/20/60 日强弱、RPS 排名和轮动矩阵。RPS 是同期相对强弱的排名，不是上涨概率。资金流功能在有明确、可用的数据源后接入。

**阶段三：接入自动选股与 Agent。** 将行业强度作为可选研究因子或候选池条件；与现有行业集中度约束共同评估。先做对照和样本外验证，再决定是否启用为默认策略条件。Agent 可引用行业快照及证据解释变化，持仓行业暴露只统计当前用户的数据。

## 7. 首版验收

- 同一交易日的抽样行业，平均涨跌幅、上涨占比、成交额均可从成员数据复算。
- 停牌、缺失、过期、未知行业、重复日线记录和不同单位的测试样本处理正确。
- 热力图、榜单、行业详情显示同一批数据，排序和选择相互一致。
- 行业筛选能正确传入既有选股器；问股携带行业、日期和事实，不自动生成未经核实的行业利好。
- 未登录和无权限访问被拒绝；不同用户的自选操作互不影响。
- 上游不可用或本地数据不全时显示真实状态，不制造排名或填充演示股票。
- 完成后端聚合与权限测试、前端类型检查和构建、真实数据浏览器验证；记录实测响应时间和覆盖数量。

## 8. 与 TSP 的关系

借鉴 TSP 的行业总览、热力图、成员联动及轮动研究流程，按本项目 Vue 3 架构实现。TSP 当前源码的行业热度和龙头评分属于手工加权规则，不直接认定为适合本项目的默认因子。
