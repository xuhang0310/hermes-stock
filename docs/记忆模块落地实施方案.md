# 记忆模块落地实施方案

> 承接 [记忆系统实施方案.md](记忆系统实施方案.md) 的三层架构(讲工程细节与 clawd 借鉴),本文聚焦**落地到 hermes-stock 的具体改动、设计理由与收益**,供直接开工或交代建者按图施工。

---

## 一、目标与定位一句话

把 hermes-stock 从"每次对话从零开始、对话超长就丢上下文、台账可被删改"的状态,升级为**三层记忆**:会话能压缩不丢主线(L1)、跨会话能记教训带样本量(L2)、台账永不可篡改(L3)。三层各自独立生命周期,互不污染,且**全部复用现有资产(向量库/调度器/推送/沙箱),只加层不重写**。

---

## 二、三层记忆架构总览

```
┌──────────────────────────────────────────────────────────┐
│ L1 会话记忆(单对话级)                                     │
│   对话超长 → 旧消息压成结构化 summary,保留 recent 4 条    │
│   多次压缩不丢历史(Previously/Newly 增量合并)            │
│   生命周期:单次对话;不跨会话                             │
├──────────────────────────────────────────────────────────┤
│ L2 经验记忆(跨会话长期)                                   │
│   复盘结论 → 经验条目(带样本量+统计强度) → 检索注入       │
│   → 成绩回填 → 无效自动降权;市场环境标签防错配           │
│   生命周期:永久但可降权归档;跨所有会话                  │
├──────────────────────────────────────────────────────────┤
│ L3 事实记忆(永久不可篡改)                                 │
│   预测台账 + LLM 调用留档,append-only JSONL + 哈希链     │
│   追加写天然不可改,哈希链让篡改可检测                    │
│   生命周期:永久;只追加不修改                              │
└──────────────────────────────────────────────────────────┘
```

| 层 | 回答的问题 | hermes-stock 现状 |
|---|---|---|
| L1 | "对话太长怎么办,前面的分析能不丢吗" | 0%,对话无压缩,超长就截断丢上下文 |
| L2 | "上次这种形态的票后来怎么样,系统能记住教训吗" | 0%,UserMemory 是用户画像不是经验库 |
| L3 | "推荐记录和 AI 调用能防篡改、可审计吗" | 0%,position_trades 可物理删除/回滚 |

## 三、落地到 hermes-stock 的具体改动

### L1 会话记忆

**新增文件**:`backend/app/ai/session_compact.py`(移植 clawd `compact.rs` 逻辑到 Python)
- `should_compact(messages, config)` — 触发判断(token 估算 ≥ 10000 且可压缩消息 > 4)
- `compact_session(messages, config)` — 主流程:旧消息→结构化 summary,保留 recent 4 条
- `summarize_messages(messages)` — 生成 `<summary>` 块(Scope/Tools/Pending/KeyFiles/CurrentWork/Timeline)
- `merge_compact_summaries(old, new)` — 增量合并不丢历史

**改现有文件**:`backend/app/ai/ai_api.py` 的 `agent_chat`
- 在每次追加消息后调用 `should_compact`,命中则 `compact_session` 替换 messages,把 summary 写成一条 `role=system` 的 continuation message
- Key files 提取规则适配 A 股(识别 6 位 SH/SZ/BJ 代码 + hermes-stock 模块路径)

**改现有表**:
- `ai_chat_messages` 加 `compaction_count INT DEFAULT 0`(被压缩了几次)
- `ai_chat_sessions` 加 `last_compacted_at DATETIME`

**参数**(沿用 clawd 默认,可调):`preserve_recent=4`、`max_estimated_tokens=10000`、summary 预算 `max_chars=1200/max_lines=24/max_line_chars=160`。

### L2 经验记忆

**新增文件**:`backend/app/ai/experience_store.py`
- `add_experience(review_id, content, tags, market_env, sample_size, strength)` — 复盘后沉淀经验(状态=observing)
- `retrieve_experiences(query, market_env, limit=3)` — 三路混合检索(标签过滤 + 向量 + rerank),相关性门槛,单次≤3
- `inject_experience(entry_id, decision_id)` — 注入留痕
- `backfill_injection(injection_id, post_return)` — 成绩回填
- `archive_stale()` — 定时降权归档(无效经验)

**复用现有**:`ai/memory.py` 的 ChromaDB/Milvus 向量层 + rerank(只复用检索基础设施,不复用 UserMemory 的语义)

**新增 3 表**:
```
experience_entries (
  id, content TEXT, tags JSON, market_env JSON,
  sample_size INT, statistical_strength FLOAT,
  status ENUM(observing/active/archived),
  source_review_id BIGINT, injected_count INT DEFAULT 0,
  avg_post_injection_return FLOAT,
  created_at, activated_at
)
experience_injections (
  id, entry_id, decision_id, injected_at, relevance_score,
  post_return FLOAT NULL, human_verified BOOL DEFAULT FALSE
)
experience_revisions (
  id, entry_id, parent_revision_id, diff TEXT, reason, created_at
)
```

**经验条目正文模板**(借鉴 clawd `<summary>` 结构化,A 股化):
```
<experience>
场景: <行业/形态/信号类型>
市场环境: <牛熊/风格>
观察: <从 N 笔复盘中归纳的事实,附 N=X>
统计强度: <置信区间/命中率>
可证伪条件: <库内字段+阈值+频率>   ← 与论点存活监测 DSL 复用
适用范围: <何时注入、何时禁用>
反例: <此前 M 次有 K 次失效的场景>
</experience>
```

**与 UserMemory 严格区分**(不混用,见下文理由)。

### L3 事实记忆

**新增文件**:`backend/app/ai/ledger_store.py`
- `append_ledger(record_type, data)` — 追加一条 record,自动算 hash(prev_hash 链式)
- `verify_ledger()` — 校验哈希链完整性(篡改可检测)
- `rotate_if_needed(path)` — 轮转(clawd 同款,台账放宽到 64MB 且不删旧)

**新增目录**:
- `data/ledger/{YYYY-MM}/{ledger-NNNNNN.jsonl}`(台账原件)
- `data/llm_calls/{YYYY-MW}/{calls-NNNNNN.jsonl}`(调用留档)

**新增 MySQL 索引表**(只读自 JSONL,供查询):
```
prediction_ledger_index (
  seq, record_type, hash, ts,
  symbol, action, status,       -- 从 JSONL data 抽出建索引
  jsonl_path, jsonl_offset
)
llm_call_index (
  seq, ts, model_version, tokens, cost, jsonl_path
)
```

**JSONL record 格式**(借鉴 clawd type 区分 + 哈希链):
```jsonl
{"type":"instruction","seq":1,"prev_hash":"0000...","hash":"a1b2...","ts":...,"data":{"action":"buy","symbol":"600519",...}}
{"type":"execution","seq":2,"prev_hash":"a1b2...","hash":"c3d4...","ts":...,"data":{"user_filled":true,...}}
{"type":"settlement","seq":3,"prev_hash":"c3d4...","hash":"e5f6...","ts":...,"data":{"excess_return":0.03,...}}
```

**改现有文件**:
- `agents/stock_agent.py` 的 LLM 调用点加 `ledger_store.append_ledger("llm_call", {...})`(顺带补方案 7.2 全量留档)
- 台账写入点(未来 P2 首席决策官下达指令时)调 `append_ledger("instruction", {...})`

## 四、为什么这么改(设计理由)

### 1. 为什么分三层,不是一层

不同生命周期的记忆混在一起,要么丢上下文要么爆存储。L1 只活一次对话(压完就丢原文保 summary),L2 跨会话永久但可降权,L3 永不可改。**各管各的,互不污染**——对话压缩不会把用户隐私写进经验库,经验库降权不会动台账,台账不可改不会阻碍对话压缩。混在一起(比如把对话历史直接当经验)是当前很多"AI 记忆"方案的通病,迟早互相污染。

### 2. 为什么 L3 用 append-only JSONL + 哈希链,不用 PostgreSQL 权限层+触发器

方案 6.1 要求台账主表禁止 UPDATE/DELETE。两条路:
- **路 A**:迁移 PostgreSQL + 收回应用账号 UPDATE/DELETE 权限 + 写触发器留痕
- **路 B(选)**:append-only JSONL + 哈希链

选 B 的理由:① 追加写天然没有修改操作,**不可篡改是结构性的,不靠自觉也不靠配置**;② 哈希链(每条带 `prev_hash`)让任何事后篡改可被 `verify_ledger()` 立即检出;③ clawd 已在生产验证追加写+原子写+轮转,不重造轮子;④ 不依赖 DBA 配权限、不触发器、不强制迁移 PostgreSQL(MySQL 继续用);⑤ 自带崩溃安全(原子写)和轮转。**台账是钱相关的,比对话严,所以比 clawd 再加一层哈希链。**

### 3. 为什么 L2 经验库与 UserMemory 严格分开

`ai/memory.py` 的 UserMemory 存的是"用户画像"(你是谁、偏好什么、做过什么决定),用于**个性化对话**。经验库存的是"统计经验"(这种形态的票此前 N 次有 K 次怎样),用于**分析师工作参考**。混用会双向污染:把用户画像注入分析师决策=引入个人偏见;把统计经验注入闲聊对话=跑题。**底层向量检索层可复用,但语义存储严格分库。**

### 4. 为什么 L1 直接移植 clawd 的 compact

clawd 的 compact 就是 Claude Code `/compact` 同款机制,经过验证。重造一个对话压缩器没有额外价值,反而容易在新造的轮子里引入 bug。**成熟零件直接用,自造的部分留给 A 股特化**(Key files 识别股票代码、summary 模板加市场环境维度)。

### 5. 为什么经验条目必须带 sample_size + statistical_strength

方案 6.5 防自欺五原则:小样本会过拟合,某信号碰巧对 5 次就加权,实则是噪音。**经验条目不带样本量和统计强度,就退化成"大模型拍脑袋的结论"**,和没有经验库一样。带样本量才能在检索时按统计强度排序、在样本不足时拒绝注入。

### 6. 为什么经验库要 market_env 标签

牛市里"追强势股"的经验注入熊市=灾难。**跨环境错配注入是经验库最大的隐性风险。** clawd 的 summary 无环境维度,经验库必须加 `market_env`(牛熊/大小盘风格),检索时先做环境过滤再向量召回。

### 7. 为什么三层都复用现有资产,只加层

hermes-stock 已有 ChromaDB/Milvus 向量层、run_sql 沙箱、rhythm_scheduler、飞书推送、多券商持仓管理。这些是沉没成本,不用白不用。**三层记忆只加 3 个新 .py 文件 + 几张表 + 几个目录**,不引入重框架(Qlib/LangGraph 那些留给自我进化方案,本方案不依赖)。

## 五、收益是什么

### 量化收益(估算)

| 收益项 | 量化 | 来源 |
|---|---|---|
| L1 单次对话 token 成本 | 降 **40~60%** | 旧消息(可能上万 token)压成 1200 字 summary |
| L1 长任务不丢上下文 | 多次压缩旧教训一直带(Previously/Newly) | 增量合并机制 |
| L3 台账不可篡改 | 篡改 **100% 可检测** | 哈希链 verify |
| L3 调用留档 | 全量 LLM 调用 **100% 落档** | append-only |
| 复用现有资产 | 向量库/调度/推送/沙箱 **0 改动** | 只加层 |
| 新增代码量 | 3 个 .py 文件 + ~5 张表 + 2 个目录 | 轻量 |

### 质化收益(对董事长讲)

1. **省钱**:对话压缩直接砍 token 账单;调用留档让"月度成本熔断""模型竞技场计分"有数据燃料(方案 7.2、6.4 的前提)。
2. **不丢上下文**:Agent 能跑长流程(比如全市场 80 只逐一分析),不会被 context 上限逼停、不会因截断把前面的分析白做。
3. **系统会记教训**:分析师判断有历史依据,不再每次从零、不再凭大模型幻觉报数;经验带样本量统计强度,防"碰巧对 5 次就加权"的自欺。
4. **钱账不可篡改**:台账+哈希链,任何事后改成绩单立即检出——这是"敢记账"的前提,没有它,自我迭代全是空转(改的是被自己篡改过的假成绩单)。
5. **经验库自己会进化**:注入留痕→成绩回填→无效自动降权,不用人工维护,坏经验不会长期污染。
6. **费用可控**:三层都轻量(append-only 文件 + 复用向量库 + 移植 clawd 逻辑),不买重框架、不迁数据库、不养新基础设施。

### 一句话收益

**L1 省钱+不丢上下文,L2 让系统长记性带统计,L3 让账本不可篡改——三层加起来,是把"每次从零的助手"变成"会攒经验、敢记账、省着花"的助手。**

## 六、落地步骤(3 期,每期独立交付与验收)

| 期 | 做什么 | 产出 | 验收 | 依赖 |
|---|---|---|---|---|
| **期1 L3** | `ledger_store.py` + JSONL/哈希链 + MySQL 索引表 + 接入 LLM 调用点 | 台账+调用留档可跑 | append 一条→verify 通过;尝试改文件→verify 报篡改 | 无,最先做 |
| **期2 L1** | `session_compact.py`(移植 compact.rs) + `ai_api.py` 触发 + 表加字段 | 对话自动压缩 | 造 20 条长消息→触发压缩→token 降;二次压缩→含 Previously compacted context | 无,可与期1并行 |
| **期3 L2** | `experience_store.py` + 3 表 + LlamaIndex 检索 + 复用向量层 | 经验库 | 注入一条经验→台账留痕;回填成绩→avg_post_injection_return 更新;观察模式不实际注入 | 期1(台账是经验成绩回填的数据源) |

**顺序逻辑**:期1 是燃料(台账是 L2 成绩回填的数据源,也是方案全部进化的前提);期2 与期1 可并行(互不依赖);期3 依赖期1。**每期独立验收,不互相阻塞。**

## 七、与现有资产复用清单

| 现有资产 | 三层中复用为 | 要改吗 |
|---|---|---|
| `ai/memory.py` 的 ChromaDB/Milvus + rerank | L2 经验库的向量召回层 | 不改,只在上层加 experience_store |
| `rhythm_scheduler` 调度器 | L2 archive_stale 定时降权 + L1 无关 | 加一个调度任务 |
| `run_sql` 沙箱 | L2 经验注入时校验数字带源ID(数字溯源) | 不改,经验注入走同一沙箱 |
| 飞书 bot 推送 | L2 经验降权/观察期满提醒 | 不改,加个推送触发点 |
| `auth` 角色权限 | L3 verify_ledger 的访问控制 | 不改 |
| MySQL(现有) | L3 索引表、L2 三张表 | 不迁 PostgreSQL |
| `position_trades`(现有) | 与 L3 台账并存——position_trades 是真实交易流水,L3 台账是**预测指令流水**,两者不冲突 | 不改 |

## 八、风险与红线

- **L1 压缩丢精度**:summary 是压缩就有损,L1 只用于对话 context 管理,**不用于台账/对账**(台账走 L3 原始 record,不走 summary)。
- **L2 经验污染**:新条目观察模式一个月、注入留痕回填、季度人工抽检检索相关性入月报;无关经验注入视为污染。
- **L2 跨环境错配**:必须带 `market_env` 标签,检索先环境过滤再向量召回,否则牛市经验注入熊市。
- **L3 哈希链不是加密**:哈希链只能检测篡改、不能防删除整个文件——L3 靠"目录只追加+权限+异地备份"补防删除,定期 `verify_ledger` 巡检。
- **红线**:L3 台账原件**永远不接 UPDATE/DELETE 接口**,任何"修正台账"的需求都走"追加一条 correction record",不就地改。
